## 4. Dependency resolution and conflict found/fixed

Installed per `runtime.md` Stage 1:
```
uv pip install --python "$PROJECT_PYTHON" 'fastmcp==4.0.3' pytest pytest-asyncio
```
This initially **broke** the scientific package's own constraint: `curve_curator`'s
`pyproject.toml` declares `pytest = "^7.4.3"` directly under `[tool.poetry.dependencies]`
(unusually, as a runtime dependency, not a dev one). The unpinned `pytest` install pulled
in `pytest==9.1.1` (dragged up transitively, not by fastmcp itself — fastmcp==4.0.3 does
not require pytest), which produced:
```
$ uv pip check --python .venv/bin/python
Found 1 incompatibility
The package `curve-curator` requires `pytest>=7.4.3,<8.0.0`, but `9.1.1` is installed
```
**Fix applied** (re-pin pytest inside the range the scientific package itself declares,
which is also within the tested range for `pytest-asyncio`):
```
uv pip install --python .venv/bin/python 'pytest>=7.4.3,<8.0.0' 'pytest-asyncio'
 - pytest==9.1.1        + pytest==7.4.4
 - pytest-asyncio==1.4.0 + pytest-asyncio==0.23.8
```
Re-checked:
```
$ uv pip check --python .venv/bin/python
Checked 96 packages in 1ms
All installed packages are compatible
```
Re-verified fastmcp still behaves correctly at this pytest version (no downgrade forced
on fastmcp/pydantic):
```
$ .venv/bin/python -c "import fastmcp; print(fastmcp.__version__)"
4.0.3
$ .venv/bin/python -c "from fastmcp import FastMCP; m=FastMCP('test'); print(m.name)"
test
```
and re-verified `curve_curator` import and the `-h` invocation still succeed after the
pytest downgrade (see command in section 3, re-run with exit status 0).

No incompatible research requirement was silently upgraded and no scientific source file
was modified to force compatibility — the fix only pinned an *additional* tool
(`pytest`) chosen by the harness back into the range the scientific package itself
requires.

## 9. Limitations / risks flagged for later stages

1. **`pytest` version must stay pinned `>=7.4.3,<8.0.0`** in this environment and in any
   future requirements files that include `curve-curator` as a runtime dependency,
   because curve_curator lists it under `[tool.poetry.dependencies]` rather than as a
   dev-only dependency. Any later worker that reinstalls or upgrades `pytest` in
   `PROJECT_ENV` without this constraint will silently reproduce the conflict found in
   section 4. Re-run `uv pip check --python "$PROJECT_PYTHON"` after any dependency
   change.
2. **No `--version` flag exists.** Downstream wrapper/tool documentation and tests must
   use `CurveCurator -h` (or the embedded `v0.6.0` string in the help/description text)
   for version evidence, not an invented `--version` flag.
3. **`available_cores` in two of the three example tomls (5) exceeds this container's 4
   logical CPUs.** Not a blocker, but Stage 2 executors should note actual wall-clock
   parallelism will be less than requested, and confirm the multiprocessing pool still
   completes successfully within any timeout they set.
4. **Stage 5 requirements.txt** must include the full curve_curator runtime stack
   (`numpy`, `pandas`, `scipy`, `statsmodels`, `bokeh`, `tqdm`, `pytest>=7.4.3,<8.0.0`,
   plus `curve-curator` itself pinned to commit `71e46f7222f825f446e9aff3fb5a3bee9473e309`
   or an equivalent documented local/pinned install), since wrappers invoke the CLI as a
   subprocess and none of these are satisfied by importing only `subprocess` in the
   wrapper module.
